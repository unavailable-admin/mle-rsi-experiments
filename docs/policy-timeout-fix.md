# MLE 并发策略超时修复

2026-10-18，APTOS 首次 online 决策在 1 秒上限下被 PolicyTimeout 阻塞。

## 证据和原因

- 旧 `legacy/mle_rsi/experiment.py` 显式设置策略时限为 8 秒；新 MLE 配置未设置，落入 Dream-RSI 通用默认的 1 秒。这是迁移配置遗漏。
- 从失败 Campaign 只读提取初始策略、tree 和 online manifest 重建首次输入。输入 1434 字节，10 次隔离运行响应均为 1.1–1.5 毫秒；不是图像训练或模型 API 超时。
- 两题共享 asyncio 事件循环，Campaign 同步持久化及其他同步工作会延迟宿主读取子进程结果。在本机双任务模拟中记录到超过 1 秒的事件循环延迟。单次存储写入也记录了同步阻塞；不能据此将全部延迟归于某个存储调用。
- 使用原策略和原输入，在宿主等待结果时注入 1.3 秒停顿：1 秒配置 3/3 次复现与现场一致的 `phase=decision; limit_s=1; returncode=-9`；8 秒配置 3/3 次正常返回。
- 原事故没有逐阶段计时，不能事后确定具体是哪次同步操作或调度延迟触发了它。复现确定了故障机制和配置回退，而非重建原事故的完整时间线。

## 修改和验证

在 `src/mle_rsi/config.py` 为 MLE search 补充 8 秒默认值；保留用户显式覆盖，不修改 Dream-RSI 通用默认、不增加无条件重试、不把超时伪装成成功。新实验也显式记录 8 秒。

新增默认值/覆盖、Campaign 和 scheduler 实际参数、宿主停顿、真实无限循环超时回归。22 项定向测试通过。修复后的本机双任务 mock 各完成一轮，策略响应最高约 1.66 秒，事件循环最大延迟约 2.58 秒，没有策略超时。模拟不涉及付费 API 或真实训练。

8 秒恢复了旧 MLE 的运行容忍度，不保证任意长度的宿主停顿都不会触发超时；超出上限仍阻塞并保留证据。详见 `docs/verification/policy-timeout-diagnosis.json`。本机复现脚本及原始记录保留在 `runs/policy-timeout-diagnosis/`。
